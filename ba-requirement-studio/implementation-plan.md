# BA Requirement Studio — পরিকল্পনা (খসড়া)

> **অবস্থা:** পরিকল্পনা — বাস্তবায়ন শুরু হয়নি · **তারিখ:** 2026-10-26
> **উদ্দেশ্য:** বিজনেস টিমের নোট/চেকলিস্ট থেকে Claude Code দিয়ে (১) ক্লায়েন্ট-শেয়ারযোগ্য ডকুমেন্ট/BRS, (২) ক্লিকযোগ্য HTML মকআপ, (৩) ডেভেলপার টাস্ক তৈরি করা, এবং অনুমোদনের পর সরাসরি **Project Tracker (pt.ibos.io)**-এ টিকিট খোলা — সব একটি নিবেদিত রিপোজিটরিতে সংরক্ষিত।

## ১. এক নজরে

```
বিজনেস টিমের নোট / চেকলিস্ট / ফাইল
        │
        ▼
/ba:peopledesk:new  ──►  স্পষ্টীকরণ প্রশ্ন (যতক্ষণ না রিকোয়ারমেন্ট পরিষ্কার)
        │
        ▼
Knowledge Base + কোডবেস বিশ্লেষণ (ডুপ্লিকেট ফিচার? প্রভাব কোথায়?)
        │
        ├──► ক্লায়েন্ট ডকুমেন্ট / BRS            (Markdown → Word/PDF/Google Docs)
        ├──► ক্লিকযোগ্য HTML মকআপ                 (PeopleDesk-এর মতো দেখতে, স্ট্যাটিক ডেটা)
        └──► ডেভেলপার টাস্ক + গ্রহণযোগ্যতার মানদণ্ড
        │
        ▼
রিভিউ ও অনুমোদন (BA লিড / প্রোডাক্ট ওনার)  ── সংশোধন হলে নতুন সংস্করণ
        │  (অনুমোদিত)
        ▼
/ba:peopledesk:publish ──► Project Tracker টিকিট (মকআপ + ডকুমেন্ট লিংকসহ) ──► Google Chat নোটিফিকেশন
```

## ২. যা ইতিমধ্যে আছে — নতুন করে বানাতে হবে না

| বিদ্যমান জিনিস | কোথায় | এই প্রকল্পে ব্যবহার |
|---|---|---|
| `/new-feature`, `/existing-feature` মোড — ইন্টারভিউ, ডুপ্লিকেট শনাক্তকরণ, Client Business Document + Developer Task | `peopledesk-kb/modes/` | রিকোয়ারমেন্ট বিশ্লেষণের মূল যুক্তি — সরাসরি পুনর্ব্যবহার |
| Knowledge Base (মডিউল, নিয়ম, API, স্ক্রিন, পারমিশন) | `peopledesk-kb/knowledge/` | ফিচার কোথায় বসবে, কী প্রভাব পড়বে |
| টেমপ্লেট: business-document, BRS, BRD, PRD, SRS, developer-task, acceptance-criteria, impact-analysis, test-cases | `peopledesk-kb/templates/` | BRS ও ক্লায়েন্ট ডকুমেন্টের কাঠামো |
| `/impact-analysis` | skill | কোন API/DB/স্ক্রিন/রিপোর্ট প্রভাবিত |
| Google Docs/Sheets এক্সপোর্ট | `/export` | ক্লায়েন্টকে পাঠানোর ফাইল |
| সাপোর্ট এজেন্টের অবকাঠামো — প্রোফাইল, CLI, লোকাল সিক্রেট কনফিগ, Google Chat (thread), Project Tracker লিংক, অডিট লগ | `peopledesk-kb/scripts/support-analyst/` | একই নকশায় BA CLI — নতুন টিমে শেয়ারও একইভাবে |
| ফ্রন্টএন্ড লেআউট — `layout/sidebar`, `layout/topNavigation`, `layout/menuComponent`, `layout/brandLogo`, `assets/menu.txt` | `app-front/src/` | মকআপের শেল টেমপ্লেট (বাঁ মেনু, টপবার, লোগো) |

> অর্থাৎ বিশ্লেষণ ও ডকুমেন্ট অংশের ৬০–৭০% প্রস্তুত; নতুন কাজ মূলত **মকআপ**, **Project Tracker সংযোগ**, **অনুমোদন প্রবাহ** ও **নতুন রিপোজিটরি**।

## ৩. তিনটি আউটপুট — বিস্তারিত

### ৩.১ ক্লায়েন্ট-শেয়ারযোগ্য ডকুমেন্ট ও BRS

- **ক্লায়েন্ট ডকুমেন্ট:** ব্যবসায়িক ভাষায়, কোনো টেকনিক্যাল বিবরণ নয় — কী সমস্যা, কী সমাধান, কারা ব্যবহার করবে, ধাপে ধাপে প্রবাহ, নিয়ম, পারমিশন, রিপোর্ট, নোটিফিকেশন, সীমাবদ্ধতা, উন্মুক্ত প্রশ্ন, মকআপের স্ক্রিনশট/লিংক।
- **BRS:** বিদ্যমান `templates/brs.md` অনুযায়ী — স্টেবল আইডি (`BR-01`, `AC-01`, `OQ-01`) যাতে টিকিট ও টেস্ট কেসে ট্রেস করা যায়।
- **ভাষা:** ক্লায়েন্টের পছন্দ অনুযায়ী বাংলা/ইংরেজি/দুটোই (সিদ্ধান্ত দরকার — §৯)।
- **ফরম্যাট:** রিপোজিটরিতে Markdown (উৎস) → শেয়ারের জন্য Word/PDF/Google Docs এক্সপোর্ট।

### ৩.২ ক্লিকযোগ্য HTML মকআপ

**লক্ষ্য:** ক্লায়েন্ট ও ডেভেলপার যেন দেখে বুঝতে পারে "কী বদলাচ্ছে" — আসল অ্যাপের মতো দেখতে ও চলতে।

**শেল (একবার তৈরি):** `app-front`-এর লেআউট দেখে একটি স্থায়ী টেমপ্লেট — বাঁ পাশের মেনু (`assets/menu.txt`/আসল মেনু কাঠামো থেকে), টপবার (প্রোফাইল, নোটিফিকেশন, বিজনেস ইউনিট/ওয়ার্কপ্লেস বাছাই), ব্র্যান্ড লোগো, রং, ফন্ট, antd-র মতো বাটন/টেবিল/ফর্ম/মোডাল।

**প্রতিটি রিকোয়ারমেন্টে:** শুধু কনটেন্ট-অংশ (পেজ বডি) নতুন — শেল একই থাকে।

**কী কী কাজ করবে (স্ট্যাটিক ডেটা দিয়ে):**

| উপাদান | আচরণ |
|---|---|
| টেবিল | সার্চ, ফিল্টার, সর্ট, পেজিনেশন, row-এ View/Edit/Delete |
| ফর্ম | ইনপুট, ড্রপডাউন, তারিখ, যাচাই-বার্তা (required, ফরম্যাট), Save করলে টেবিলে যোগ |
| মোডাল/ড্রয়ার | Create/Edit/Confirm |
| অ্যাপ্রুভাল | Pending → Approved/Rejected অবস্থা বদল |
| ন্যাভিগেশন | মেনু ও বাটন থেকে মকআপের অন্য স্ক্রিনে যাওয়া |
| টোস্ট/অ্যালার্ট | সফল/ব্যর্থতার বার্তা |
| "নতুন/পরিবর্তিত" চিহ্ন | ঐচ্ছিক হাইলাইট — কোন অংশ নতুন তা দেখাতে (ক্লায়েন্ট ভার্সনে বন্ধ করা যায়) |

ডেটা ব্রাউজারের মেমরিতে থাকে — কোনো সার্ভার/API নয়; রিফ্রেশে শুরুর ডেটায় ফেরে।

**প্রযুক্তিগত বিকল্প:**

| বিকল্প | সুবিধা | অসুবিধা |
|---|---|---|
| **A. React 18 + antd 4 (CDN), একটি HTML ফাইল** — *সুপারিশ* | আসল অ্যাপের মতো উপাদান ও আচরণ; একক ফাইল, অফলাইনে খোলে; build লাগে না | CDN সংস্করণ পিন করতে হবে; MUI/কাস্টম CSS-এর কিছু অংশ হুবহু হবে না |
| B. সাধারণ HTML/CSS + vanilla JS | হালকা, নির্ভরতা নেই | antd-র মতো টেবিল/ফর্ম হাতে বানাতে হবে, ধারাবাহিকতা কঠিন |
| C. `app-front`-এর ভেতরে মক-ডেটা রুট | সবচেয়ে হুবহু | প্রোডাক্ট কোডে মিশে যায়, build/deploy লাগে, BA টিম স্বাধীনভাবে চালাতে পারে না |

**মকআপ কিট:** শেলের সাথে পুনর্ব্যবহারযোগ্য উপাদান (লিস্ট পেজ, ফর্ম পেজ, অ্যাপ্রুভাল পেজ, রিপোর্ট পেজ) — প্রতিটি মকআপ যেন একই রকম দেখায় ও দ্রুত তৈরি হয়।

### ৩.৩ ডেভেলপার টাস্ক ও Project Tracker টিকিট

- বিদ্যমান `developer-task.md` অনুযায়ী — দায়িত্ব, আর্কিটেকচারাল প্রভাব, প্রয়োজনীয় টেস্ট, গ্রহণযোগ্যতার মানদণ্ড।
- **অনুমোদনের পরেই** Project Tracker-এ টিকিট — শিরোনাম, বিবরণ, মডিউল/সাবমডিউল, অগ্রাধিকার, টাস্কের ধরন, (ঐচ্ছিক) স্প্রিন্ট/দায়িত্বপ্রাপ্ত, সংযুক্তি/লিংক: মকআপ, BRS, ক্লায়েন্ট ডকুমেন্ট।
- টিকিট তৈরি হলে টিকিট নম্বর রিপোজিটরিতে ফেরত লেখা হয় এবং Google Chat-এ কার্ড (সাপোর্ট এজেন্টের মতো thread)।

## ৪. নতুন রিপোজিটরির কাঠামো (প্রস্তাব)

নাম উদাহরণ: `peopledesk-ba-studio` (চূড়ান্ত নাম আপনার সিদ্ধান্ত)।

```
peopledesk-ba-studio/
├── README.md                     # কীভাবে ব্যবহার, কমান্ড, নিয়ম
├── CLAUDE.md                     # এজেন্টের নিয়ম (ভাষা, অনুমোদন, ডেটা গোপনীয়তা)
├── mockup-kit/
│   ├── shell.html                # PeopleDesk লেআউট — মেনু, টপবার, লোগো
│   ├── kit.js / kit.css          # তালিকা/ফর্ম/মোডাল/অ্যাপ্রুভাল উপাদান
│   └── examples/                 # নমুনা পেজ
├── templates/                    # ক্লায়েন্ট ডকুমেন্ট, BRS, ডেভ টাস্ক, PT টিকিট
├── tools/ba-cli/                 # CLI: মকআপ যাচাই, এক্সপোর্ট, PT টিকিট, Chat — টেস্টসহ
├── profiles/                     # প্রোডাক্টভিত্তিক (PeopleDesk, Managerium …)
└── requirements/
    └── REQ-2026-0001-leave-encashment/
        ├── 00-input/             # বিজনেস টিমের আসল নোট/ফাইল (অপরিবর্তিত)
        ├── 01-analysis.md        # স্পষ্টীকরণ, অনুমান, প্রভাব, ডুপ্লিকেট যাচাই
        ├── 02-client-document.md
        ├── 03-brs.md
        ├── 04-developer-task.md
        ├── mockup/index.html     # ক্লিকযোগ্য মকআপ
        ├── exports/              # .docx / .pdf
        ├── status.json           # Draft → Review → Approved → Ticketed, সংস্করণ, PT টিকিট নম্বর
        └── CHANGELOG.md          # প্রতিটি সংশোধনের ইতিহাস
```

রিভিউ Git দিয়ে: প্রতিটি রিকোয়ারমেন্ট একটি branch/PR → BA লিড রিভিউ করে merge = অনুমোদন (বা আলাদা `/ba:peopledesk:approve`)।

## ৫. কমান্ড (প্রস্তাব)

| কমান্ড | কাজ |
|---|---|
| `/ba:peopledesk:new <নোট বা ফাইল>` | নতুন রিকোয়ারমেন্ট — স্পষ্টীকরণ প্রশ্ন, বিশ্লেষণ, তিনটি আউটপুট খসড়া |
| `/ba:peopledesk:revise REQ-…  <পরিবর্তন>` | মন্তব্য অনুযায়ী সংশোধন, নতুন সংস্করণ, CHANGELOG |
| `/ba:peopledesk:mockup REQ-…` | শুধু মকআপ তৈরি/হালনাগাদ |
| `/ba:peopledesk:export REQ-…` | Word/PDF/Google Docs |
| `/ba:peopledesk:approve REQ-…` | অনুমোদন রেকর্ড (কে, কখন) |
| `/ba:peopledesk:publish REQ-…` | **শুধু অনুমোদিত** রিকোয়ারমেন্টে Project Tracker টিকিট + Chat |
| `/ba:peopledesk:status` | সব রিকোয়ারমেন্টের অবস্থা |

**নামকরণ:** `/ba:<প্রোডাক্ট>:<কাজ>` — প্রোডাক্টের নাম কমান্ডেই থাকে, তাই ভুল প্রোডাক্টে কাজ হওয়ার ঝুঁকি নেই এবং অন্য টিম একই কাঠামো পায় (`/ba:managerium:new`, `/ba:apon:new` …)। Claude Code ফোল্ডার থেকে নাম তৈরি করে: `~/.claude/commands/ba/peopledesk/new.md` → `/ba:peopledesk:new`; সাপোর্ট এজেন্টের মতো প্রোডাক্ট প্রোফাইল থেকে `install.sh` সব কমান্ড তৈরি করবে। দুই স্তরের ফোল্ডার-নাম বাস্তবায়নের শুরুতে যাচাই করা হবে; কাজ না করলে বিকল্প `/ba:peopledesk-new`।

## ৬. কাজের প্রবাহ ও অবস্থা

| অবস্থা | কে | কী হয় |
|---|---|---|
| `DRAFT` | BA + Claude | নোট থেকে খসড়া, স্পষ্টীকরণ |
| `IN_REVIEW` | BA লিড / প্রোডাক্ট ওনার | ডকুমেন্ট ও মকআপ রিভিউ, মন্তব্য |
| `CLIENT_REVIEW` (ঐচ্ছিক) | ক্লায়েন্ট | ক্লায়েন্ট ডকুমেন্ট + মকআপ দেখে সম্মতি |
| `APPROVED` | অনুমোদনকারী | পরিবর্তন বন্ধ (নতুন পরিবর্তন = নতুন সংস্করণ) |
| `TICKETED` | `/ba:peopledesk:publish` | PT টিকিট নম্বর রেকর্ড, Chat নোটিফিকেশন |
| `IN_DEVELOPMENT` / `DONE` | PT থেকে | (পরবর্তী ধাপ) PT-র অবস্থা ফেরত পড়া |

**কঠোর নিয়ম:** অনুমোদন ছাড়া কখনো PT টিকিট নয়; একই রিকোয়ারমেন্টে দ্বিতীয় টিকিট নয় (idempotent); মকআপে কখনো আসল ক্লায়েন্ট ডেটা নয়।

## ৭. ব্লকার ও চ্যালেঞ্জ

### ৭.১ মূল ব্লকার (সমাধান ছাড়া শুরু করা যাবে না)

| # | ব্লকার | কেন সমস্যা | প্রস্তাবিত সমাধান |
|---|---|---|---|
| B1 | **Project Tracker-এ টিকিট তৈরির উপায়** | PT-র টাস্ক অনেক টেবিলে ছড়ানো — `tblTaskMain` (১৬,২১৭), `tblTaskDetails`, `tblTaskResource`, `tblTaskActivityLog`, `tblTaskHistory`, `tblSprint`, `tblSetTaskStatus` … সরাসরি DB-তে insert করলে PT-র নিজস্ব নিয়ম, লগ, নোটিফিকেশন বাদ পড়বে, ডেটা অসামঞ্জস্য হবে | **PT-র API** (pt.ibos.io যে API ব্যবহার করে) + একটি সার্ভিস অ্যাকাউন্ট/টোকেন। PT টিমের কাছ থেকে "টাস্ক তৈরি" endpoint, অনুমোদন পদ্ধতি ও ফিল্ডের নিয়ম লাগবে। সরাসরি DB insert শুধু শেষ বিকল্প, PT টিমের অনুমোদিত SP দিয়ে |
| B2 | **PT ফিল্ড ম্যাপিং** | প্রজেক্ট, মডিউল/সাবমডিউল (`tblSetModule` ১,৫৯২, `tblSetSubModule` ১৪,৯৮৭), টাস্কের ধরন (`tblTaskType`), অগ্রাধিকার, স্প্রিন্ট, দায়িত্বপ্রাপ্ত — কোনটা বাধ্যতামূলক, কোন আইডি | PT টিমের সাথে বসে একটি ম্যাপিং টেবিল প্রোফাইলে রাখা |
| B3 | **নতুন রিপোজিটরি** | বর্তমান `peopledesk-kb` "শুধু Markdown" নিয়মের; HTML মকআপ ও CLI-র জন্য আলাদা জায়গা দরকার | আপনি রিপোজিটরি তৈরি করে লিংক দেবেন (আপনি উল্লেখ করেছেন) |
| B4 | **অনুমোদনকারী কে** | কে "Approved" বলবে, কে PT টিকিট খুলতে পারবে | ভূমিকা নির্ধারণ — BA লিড, প্রোডাক্ট ওনার |

## ৯. আপনার কাছ থেকে যা লাগবে

1. **নতুন রিপোজিটরির নাম ও লিংক** (যেমন `peopledesk-app/peopledesk-ba-studio`)।
2. **Project Tracker API:** টাস্ক তৈরির endpoint, অনুমোদন (টোকেন/সার্ভিস অ্যাকাউন্ট), বাধ্যতামূলক ফিল্ড — অথবা PT টিমের একজন যোগাযোগকারী।
3. **PT ম্যাপিং:** PeopleDesk-এর প্রজেক্ট আইডি, ডিফল্ট টাস্কের ধরন, অগ্রাধিকার, স্প্রিন্ট নীতি, ডিফল্ট দায়িত্বপ্রাপ্ত।
4. **অনুমোদনকারী:** কে রিভিউ করবে, কে টিকিট খুলতে পারবে।
5. **ক্লায়েন্ট ডকুমেন্টের ভাষা ও নমুনা:** পছন্দের একটি পুরনো ডকুমেন্ট থাকলে খুব সহায়ক।
6. **মকআপ শেয়ারের পদ্ধতি:** ফাইল সংযুক্তি, প্রাইভেট লিংক, নাকি অভ্যন্তরীণ হোস্টিং।
7. **BA টিমের Google Chat space-এর webhook** (ঐচ্ছিক) — `setup` দিয়ে, chat-এ নয়।
8. **২–৩টি আসল নমুনা নোট** (বিজনেস টিমের) — প্রথম পাইলটের জন্য।

## ১০. সফলতার মাপকাঠি

- নোট থেকে প্রথম পূর্ণ খসড়া (ডকুমেন্ট + মকআপ + টাস্ক) — **এক কর্মদিবসের কম সময়ে**।
- রিভিউতে বড় সংশোধন কমে আসা (সংস্করণ সংখ্যা)।
- ডেভেলপারের "রিকোয়ারমেন্ট বুঝিনি" প্রশ্ন কমে আসা।
- অনুমোদিত প্রতিটি রিকোয়ারমেন্টের PT টিকিট ও ট্রেসেবল `AC-` → টেস্ট কেস।

## ১১. উদাহরণ — একটি রিকোয়ারমেন্টের যাত্রা

1. বিজনেস টিম লেখে: *"Leave encashment — বছর শেষে অব্যবহৃত Earned Leave টাকায় রূপান্তর, সর্বোচ্চ ১৫ দিন, Basic অনুযায়ী, HR অনুমোদন লাগবে।"*
2. `/ba:peopledesk:new` — Claude প্রশ্ন করে: কোন leave type? ১৫ দিন প্রতি বছর না মোট? Basic না Gross? Payroll-এ কোন মাসে? Knowledge Base দেখে জানায় `Timesheets/Leave/Encashment` ইতিমধ্যে আছে → `existing-feature` হিসেবে এগোয়।
3. তৈরি হয়: ক্লায়েন্ট ডকুমেন্ট (বাংলা), BRS (`BR-01…`, `AC-01…`), মকআপ — Leave Encashment তালিকা, আবেদন ফর্ম, HR অনুমোদন স্ক্রিন — সব ক্লিকযোগ্য, নমুনা কর্মী দিয়ে।
4. BA লিড রিভিউ → ১টি সংশোধন → `APPROVED`।
5. `/ba:peopledesk:publish` → PT টিকিট `TKT-…` (মকআপ ও BRS সংযুক্ত) → Google Chat-এ কার্ড।
6. ডেভেলপার PT টিকিট থেকে মকআপ খুলে দেখে কাজ শুরু করে।

## ১২. সিদ্ধান্তের জন্য আমার সুপারিশ

- মকআপ: **বিকল্প A** (React 18 + antd 4 CDN, একক HTML) — আসল অ্যাপের সবচেয়ে কাছাকাছি, BA টিম স্বাধীনভাবে চালাতে পারবে।
- PT: **API দিয়ে**, সরাসরি DB insert নয়।
- অনুমোদন: **Git PR-এ রিভিউ** + `/ba:peopledesk:approve` রেকর্ড — কে কখন অনুমোদন দিল তা স্থায়ীভাবে থাকে।
- পাইলট: একটি ছোট আসল রিকোয়ারমেন্ট দিয়ে ধাপ ১–৫, তারপর PT সংযোগ।
